# Concurrency – One-Page Study Notes

## What is Concurrency?

**Concurrency** is when multiple tasks make progress during the same period of time. They may not run at exactly the same instant.

* **Concurrency** = dealing with many tasks at once.
* **Parallelism** = multiple tasks executing simultaneously on multiple CPU cores.

> A single-core CPU can be concurrent by rapidly switching between tasks.

---

## Why Use Concurrency?

✅ Improve responsiveness (UI remains usable)

✅ Better CPU utilisation

✅ Handle many users/processes simultaneously

✅ Overlap computation with I/O

Examples:

* Web servers handling thousands of requests
* Video games updating graphics while processing input
* Operating systems running many applications

---

## Process vs Thread

| Process                 | Thread                           |
| ----------------------- | -------------------------------- |
| Independent program     | Execution path within a process  |
| Own memory space        | Shares memory with other threads |
| Heavyweight             | Lightweight                      |
| Communication is slower | Communication is fast            |

**One process can contain many threads.**

---

## Thread States

```
New
 ↓
Ready
 ↓
Running
 ↙      ↘
Blocked  Ready
 ↓
Ready

```

* **Ready** – waiting for CPU
* **Running** – executing
* **Blocked** – waiting for I/O or resource

---

## Context Switching

A **context switch** occurs when the operating system saves one thread's state and loads another.

Costs:

* CPU overhead
* Cache disruption
* Too many switches reduce performance

---

# Synchronisation

Used when multiple threads share data.

Without synchronisation:

```
Counter = 5

Thread A reads 5
Thread B reads 5

Both add 1

Both write 6
```

Expected: **7**

Actual: **6**

This is a **race condition**.

---

## Critical Section

A **critical section** is code that accesses shared data.

Only **one thread** should execute it at a time.

---

## Mutex (Mutual Exclusion)

A mutex allows only one thread into a critical section.

```
lock()

update shared data

unlock()
```

---

## Semaphore

A semaphore controls access to a limited number of resources.

Example:

* Printer pool
* Database connections
* Parking spaces

Counting semaphore:

```
wait()
  use resource
signal()
```

---

## Deadlock

Occurs when threads wait forever for each other.

Example:

```
Thread A:
Lock X
Wait for Y

Thread B:
Lock Y
Wait for X
```

Neither can continue.

### Four Deadlock Conditions

1. Mutual exclusion
2. Hold and wait
3. No preemption
4. Circular wait

Preventing any one condition prevents deadlock.

---

## Starvation

A thread never gets CPU time or a needed resource because others keep being chosen.

**Different from deadlock:** the system still runs.

---

## Livelock

Threads continue changing state but make **no useful progress**.

Example:
Two people repeatedly stepping aside for each other in a hallway.

---

# Common Problems

### Race Condition

Multiple threads modify shared data unexpectedly.

### Deadlock

Threads wait forever.

### Starvation

A thread never gets resources.

### Livelock

Threads keep reacting but accomplish nothing.

---

# Best Practices

✔ Keep critical sections short

✔ Minimise shared data

✔ Acquire locks in a consistent order

✔ Avoid unnecessary locking

✔ Prefer thread-safe data structures where available

# Key Exam Terms

| Term             | Definition                                                 |
| ---------------- | ---------------------------------------------------------- |
| Concurrency      | Multiple tasks making progress during the same time period |
| Parallelism      | Tasks executing simultaneously on multiple CPU cores       |
| Thread           | Lightweight execution unit within a process                |
| Process          | Independent program with its own memory                    |
| Context Switch   | CPU switches between threads/processes                     |
| Critical Section | Code accessing shared data                                 |
| Mutex            | Allows one thread at a time                                |
| Semaphore        | Controls access to multiple resources                      |

| Starvation       | Thread never receives required resources                   |
| Livelock         | Threads remain active but make no progress                 |

## Memory Trick

**Concurrency Problems**

* 🏁 **Race** = Wrong result
* 🔒 **Deadlock** = Nothing moves
* 🍽️ **Starvation** = Someone never gets served
* 🚶 **Livelock** = Everyone moves, nobody progresses

**Remember:** Synchronisation tools (mutexes and semaphores) solve race conditions, but if used poorly they can introduce deadlocks or starvation.
